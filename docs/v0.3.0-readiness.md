## Repo size (~97 MB, corpus STLs)

- The growth is the 40-mesh `tests/real-world-samples/` corpus (~97 MB of STLs;
  the 115-mesh scan corpus at `/tmp/sutura_corpus_100/` is NOT committed).
- **GitHub can host this** (100 MB per-file limit; 97 MB total is comfortably
  under it), but it is large for a code repo and the packed `.git` will grow
  alongside. STLs compress reasonably well (expect ~150–200 MB packed).
- **Recommendation:** acceptable to push as-is for v0.3.0; if the corpus keeps
  growing (more Thingi10K/Artec samples), migrate `*.stl` to Git LFS or move
  the corpus out-of-repo with a download script. Decision is the maintainer's;
  this is not a blocker, just a size-consciousness note.

## `--experimental-join-components`: promote to the main chain?

**Recommendation: keep it behind the flag for v0.3.0 — do not promote.**

- It changes geometry by **translating** debris onto the nearest larger
  component. Deleting scan debris is almost always the correct repair; joining
  is a niche need (separate shells that *should* connect), and a wrong join
  distorts the model in a way a delete never would.
- The prototype is **not corpus-tested** (not in CI, not run over the 115-mesh
  corpus) — it only has the smoke test. Promoting it without corpus evidence
  would violate the "conservative defaults" stance the pipeline has held.
- Suggested evaluation path (later, not tonight): run the 115-mesh corpus with
  the flag and compare strict-watertight + geometry-change against the default
  chain; only if it shows a clear win on a defined subset (e.g. multi-shell
  scans) reconsider.

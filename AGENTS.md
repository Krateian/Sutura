# AGENTS.md

Sutura: two-stage STL/3MF mesh repair for 3D printing. Stage 1 = PyMeshLab
(VCG filter chain), stage 2 = manifold3d solid rebuild. Git repo, branch
`main`, remote `Krateian/Sutura`.

## How it runs

- Real entry point is `sutura/repair.py` (JSON report to stdout; `--human` for a readable report; exit 0 on success or a stage-1-only partial, exit 1 on a hard error like malformed input). `bin/sutura` is only a bash wrapper: `exec $HOME/.local/share/sutura/venv/bin/python .../repair.py "$@"`. Two read-only modes share the same entry point: `sutura validate model.stl` (first positional arg `validate`) analyzes without repairing, and `sutura model.stl --dry-run` reports the would-do plan — both write NO output file. Mode/eşik resolution for repair AND dry-run comes from the shared `repair.resolve_mode_params(mode, type, conf)` (single source of truth, like classification.py).
- `repair.py` imports `pymeshlab` *inside* functions, not at module top, so running it with the plain system Python fails. It must run under the `~/.local/share/sutura/venv` interpreter (PyMeshLab), which talks to `venv311` (python3.11) for stage 2 via `sutura/manifold_bridge.py` as a subprocess.
- `install.sh` creates both virtualenvs (`venv` with PyMeshLab from `requirements.txt`, `venv311` with manifold3d from `requirements-311.txt`), copies the source into `~/.local/share/sutura/`, and installs `~/.local/bin/sutura`. Re-running is safe. It bails if no `python3.11` is available (manifold3d ships wheels only up to Python 3.13).
- **AppImage build (alternative distribution):** `scripts/build_appimage.sh` bundles two relocatable python-build-standalone runtimes (Python 3.14 -> `usr/lib/sutura/venv`, Python 3.11 -> `usr/lib/sutura/venv311`) plus the app modules and builds `dist/Sutura-x86_64.AppImage` with appimagetool (which carries its own `mksquashfs`, so no system package needed). The AppRun dispatch exports `SUTURA_DIR`/`SUTURA` so `repair.py` finds its venv311/bridge and `gui.py` finds its CLI without code changes. **AppImage mode detection:** `updater.py` checks the `APPIMAGE` env var (set by the AppImage runtime); in that mode the GUI skips the first-run ask / background checks and the update button shows a "download from releases" message instead of self-updating (self-update cannot write to a read-only squashfs). `updater.py`'s VERSION fallback reads `repair.py` beside itself before the host install dir so the bundled copy is authoritative.
- Multi-object 3MF files are repaired object-by-object in memory (numpy arrays), preserving the original archive structure. An object that stage 1 closes gets a **per-object stage 2** watertight rebuild through the shared `repair.maybe_run_stage2` helper (the same gate/OBJ round-trip as single-mesh files); per-object `stage2` reports, `objects_watertight`/`objects_stage2_ok` aggregates, and an ALL-objects file verdict (`classification._classify_objects`) were added in the same change that fixed the layered-mesh Stage-1 collapse. Single-mesh files round-trip through OBJ for stage 2. Byte-identical objects reuse one repair (geometry cache) but each still gets its own per-object report.
- Read-only analysis lives in `repair.validate_file` / `repair.dry_run_file` (per-mesh: `validate_mesh_from_arrays` / `dry_run_mesh_from_arrays`), both sharing `repair.load_meshes` (STL/OBJ via pymeshlab, 3MF via `parse_3mf_meshes`). `scan_bad_coordinates` skips `.3mf` (its XML parser silently drops non-numeric vertices) and is also the reason single-object 3MF repair works — do not make it treat 3MF as STL again.
- **Usage history (anonymous, opt-out):** `sutura/history.py` (stdlib+numpy, no pymeshlab) records a purely-technical repair log to `~/.local/share/sutura/history.jsonl` — mesh sizes, defect counts, classifier outcome, mode, category, confidence, timing + a quantized geometry `mesh_fingerprint` (sha256, for dedup). HARD RULE: never store file names/paths/users/IPs — `repair_file`/`repair_3mf` compute the fingerprint and stash it as a transient `report['_fp']` key; `process_file` always runs `history.pop_fingerprints(result)` (so `_fp` never leaks into the JSON stdout report) and, unless `--no-history`, `history.write(...)` (which swallows its own errors — recording never breaks a repair). validate/`--dry-run` never record. `sutura export-history` prints a summary + the full JSON array (one command; `--summary-only`/`--last N`/`--clear`). GUI: `updater.py` `DEFAULT_CONFIG['history_enabled']` (default true) drives the first-run dialog checkbox and `RepairWorker` adding `--no-history`. history.py must stay in the explicit module lists of `install.sh`, `install-macos.sh` and `scripts/build_appimage.sh`.
- The GUI (`sutura/gui.py`, PySide6) just shells out to the installed `sutura` CLI and parses the last stdout JSON line. Its **Repair Mode** picker (a small "Mode: Auto" button next to the heatmap/before-after buttons) opens `RepairModeDialog`: a five-step horizontal QSlider (low/medium/auto/aggressive/extreme) with a live localized description and OK/Cancel. The mode is stored **batch-wide** on the MainWindow (`self._repair_mode`, default `auto`), not per file, and `RepairWorker` passes it to the CLI as `--mode <mode>`; the chosen mode must therefore be verified in the JSON `repair_mode` of the batch results, not in per-file state.
- Result classification lives in `sutura/classification.py` (stdlib-only, no numpy/pymeshlab): `classify()` returns `(category, issues, summary_key)` and both the CLI (`repair.py`) and the GUI (`gui.py`) import it so they never diverge. "Watertight" is only claimed when stage 2 actually ran and returned `ok`; a stage-1-closed mesh with stage 2 skipped/errored/never-run (e.g. macOS in-process fallback unavailable) is a warning. CLI `--human`/JSON label issues via this module (English, not localized); the GUI localizes the same codes through its EN/TR dictionary.
- `sutura/confidence.py` (stdlib-only) computes the repair confidence score: `repair_confidence()` (post-repair, category-anchored, stage 2 dominant, hard errors forced to 0/low) and `estimate_confidence_pre_repair()` (validate / `--dry-run` estimate, missing signals ignored). It lazy-imports the tuning gates from `repair.py` (`MECH_TUNE_GATE`/`ORG_TUNE_GATE`) so the score can never drift from the real repair thresholds; shared by the CLI and the GUI.
- `sutura/defects.py` (stdlib+numpy only) detects the input mesh's holes and non-manifold regions from plain `verts`/`tris` arrays; `repair.py` calls `detect()` on the input and stores it in the report's `defects` key (always in JSON; `--human` only with `--defects`). The GUI renders the selected file's defects in a panel below the log. Keep it free of pymeshlab/trimesh so it stays importable anywhere. `detect(..., with_indices=True)` additionally returns each defect's `verts_idx`/`faces_idx` index lists for the heatmap; the CLI uses the default (False) so its JSON contract is unchanged.
- `sutura/heatmap.py` (numpy + Qt QImage/QPainter only, no pymeshlab) is the defect heatmap rasterizer: it projects the mesh with an auto-fit orthographic isometric camera, depth-sorts faces (painter's algorithm) and fills each face red when it touches a defect vertex, grey otherwise (~250k tris/s on CPU). It is deliberately a **CPU rasterizer, not OpenGL**: offscreen GL draw calls (`glDrawArrays`/`glDrawElements`) segfault on headless systems (verified on an NVIDIA box without a display) and can be unavailable in the AppImage/macOS CI. Do not replace it with GL without re-checking that. `render(...)` also accepts an optional `frame=(center, scale)` from `shared_frame(verts_list, w, h, pad)` so several meshes can be rendered with the IDENTICAL camera (used by the before/after comparison), and `focus_frame(verts, verts_idx, w, h, pad, fill=0.75)` returns a zoomed frame centered on a defect region (its vertices' view-space bbox) for the before/after detail close-up.
- `sutura/heatmap_render.py` is a CLI entry run as a **subprocess** by the GUI's `HeatmapWorker` to load+detect+rasterise a heatmap into a PNG temp file. This isolation is required: using pymeshlab inside a Qt worker thread while a `QMainWindow` exists corrupts the heap at interpreter shutdown (PySide6 6.11 + Python 3.14). The GUI process therefore never imports pymeshlab. The GUI shows a "Show heatmap" button + clickable thumbnail (on-demand, cached per file; first object for multi-object 3MF) and falls back silently to the text-only panel on any failure.
- `sutura/before_after_render.py` is a second subprocess CLI entry (spawned by the GUI's `BeforeAfterWorker`) that loads the original AND repaired mesh, detects defects on BOTH, and writes FOUR PNGs: before (original defects red on grey), after (tri-state: grey = never broken, green `(46,204,113)` = healed, orange `(255,140,60)` = still broken), detail_before + detail_after (close-up of the WORST original defect region by physical bounding-box diagonal, both with the same zoomed frame from `heatmap.focus_frame`). **Camera: it is NOT the fixed isometric view** — the shared camera is directed toward the worst ORIGINAL defect's centroid via `heatmap.defect_camera(center, worst['centroid'])` so the defect never hides behind the mesh; the two-stage `shared_frame` call first yields the rotation-independent world-space bbox centre, then the real `(center, scale)` frame with that rotation so the scale fits R's view axes. `_ISOMETRIC` is used only when the mesh is clean or the defect sits at the bbox centre (R is None). Known limitation: on extremely asymmetric meshes (long/thin, dumbbell-like) the defect-facing angle can collapse the view-space bbox and render the mesh small — deferred to the v0.2 interactive 3D viewer (user-fixable), NOT improved now. Because repair changes topology (before/after indices differ), "healed" is a SPATIAL classification via `before_after_render.healed_face_mask(rverts, rtris, old_defects, overts, rep_defects, cap=256, halo=1.5)` (pure numpy, loops over defects / vectorizes over faces with buffer reuse): a repaired face is healed when it lies within 1.5× its real extent (max |v - centroid| from verts_idx, NOT diameter) of an original defect centroid and the repaired mesh's own detect() reports no defect there; only the `cap` largest defects drive the green highlight (still-broken orange is uncapped, full-resolution from rep_defects). `heatmap.render` gained an optional `healed=(M,)` mask + `healed_color` (default green) — defect faces win precedence; heatmap_render.py stays unchanged (backward compatible). No original defects -> detail mirrors the main views. The GUI's "Show before/after" button opens a dialog with the main image + a smaller detail close-up below it and ONE toggle button flipping both between Original/Repaired. Static CPU-rendered pair — NOT an interactive 3D slider, for the same GL-segfault reason as the heatmap.
- `sutura/viewer_common.py` is the shared pure-numpy+Qt helper module for the before/after comparison: `defect_vertex_set`, `broken_face_mask`, `healed_face_mask`, `defect_diagonal`, `worst_defect`, `initial_view_camera` (returns the defect-facing `rotation` + `(center, scale)` frame that BOTH the static and interactive views open with) plus the `ORANGE`/`GREEN`/`HEALED_CAP`/`HEALED_HALO` constants. It imports `heatmap` for the camera helpers; no pymeshlab. `before_after_render.py` re-exports these (its `healed_face_mask` is still the name `tests/test_healed_mask.py` imports), and `viewer_data_render.py` uses them directly.
- `sutura/viewer_data_render.py` is the LAZY subprocess CLI that builds the interactive-viewer dataset (spawned by the GUI's `ViewerDataWorker` the FIRST time the user picks "Interactive"; the npz is cached for the dialog's lifetime and dropped when the dialog closes — no persistent cache). It loads both meshes with pymeshlab, detects defects, computes healed masks, decimates each mesh to an interactive LOD (**`LOD_TARGET=3500`** via `meshing_decimation_clustering`; threshold steps `(0.5, 1.0, 2.0, 4.0, 8.0)`, closest-to-target wins), computes the surface-deviation distance with pymeshlab's `compute_scalar_by_distance_from_another_mesh_per_vertex` (measure=repaired, ref=original, `signeddist=False`; per-vertex unsigned nearest-surface distance — no scipy/rtree needed) plus `get_hausdorff_distance` for the global max, and writes ONE npz: full+LOD verts/tris for both meshes, `defect_vidx`/`broken_vidx` vertex lists, `healed`/`lhealed` masks, `distance`/`ldistance` arrays, `hausdorff`, the shared `frame_center`/`frame_scale`, `initial_rotation` (3x3, all-zero when the mesh is clean -> isometric fallback) and `viewport_w/h`. Regressed by `tests/test_viewer_data.py`. Measured on the 75-model corpus: the default `draw_frame` path at LOD 3500 gives median ~71 FPS, min 43.8 FPS, no model under 30 FPS (720x540).
- **Interactive viewer (v0.2).** `heatmap.render` is now a wrapper over `prepare_render` (one-time per mesh+mode: normals, lighting LUTs, defect/healed masks, deviation ramp -> a `RenderContext`) + `draw_frame(ctx, rotation, scale)` (per-frame: project + z-sort + QPainter) — byte-identical regression gate in `tests/test_heatmap.py`. A per-vertex `deviation` array drives the "surface deviation" view via `deviation_quantile_index` + `_deviation_lut` (navy->cyan->yellow->red, quantile-scaled); defect faces always win over the ramp. The GUI process renders interactively with `gui.py`'s `MeshViewport` (drag = yaw/pitch orbit via `_orbit_basis`, wheel = zoom `scale` override; LOD drawn during drag, ~300 ms idle -> full-res "final" frame) on a `_RenderThread` (latest-wins frame dropping, numpy+QPainter only — pymeshlab is NEVER in this thread or the GUI process). `_open_before_after` keeps the STATIC view as the default first view and adds a Static/Interactive radio switch; the interactive npz is built lazily and cached per dialog. Deviation mode only recolors the repaired side; still-broken faces stay orange on top; the Hausdorff max is shown as a label.
- `sutura/mesh_classifier.py` (stdlib+numpy only) heuristically classifies a mesh as `mechanical`/`organic`/`unknown` from dihedral-angle geometry. Its confidence is a **signed-margin score**: sigmoid memberships over three corrected dihedral bands (near90 `[60,120]°`, true-flat `<1°`, gentle-curvature `[1,15)°`; mechanical = max/OR of near90 & flat signals, organic = min/AND of low near90, low flat, high gentle), decisions at fixed floors (`mechanical >= 0.7`, `organic >= 0.5`), and `unknown` carries a non-zero proximity value + `metrics['leaning']` instead of a flat 0. NOTE: the edge→face pairing uses `i % F` (the concatenated edge array is block-stacked, not per-face); the old `i // 3` paired up unrelated faces and produced garbage near90/coplanar — the old `coplanar` metric was replaced by the `flat`/`gentle` split precisely so smooth high-poly organics (dihedrals ~2-5°, i.e. `gentle`) never read mechanical. `repair_mesh_from_arrays` calls it and, on non-`unknown`, tunes two Stage 1 thresholds (`mincomponentsize`, `maxholesize`) via the module-level `_TYPE_PARAMS` table in `repair.py` — but only when confidence clears the **class-specific tuning gate** (`repair.MECH_TUNE_GATE=0.75`, `repair.ORG_TUNE_GATE=0.70`, helper `repair.tuning_applied_for`): below the gate the detected type is still reported but the conservative default thresholds are used, and the report carries `tuning_applied` (true/false; shown in `--human` and the GUI defect panel). Both gates sit just above the worst correct prediction on the corrected set (mechanical min 0.867, organic min 0.693) — the old `0.55` organic gate and its "structurally capped at ~0.62" rationale were artifacts of the pairing bug. Those per-type values are EXPERIMENTAL/uncalibrated starting points (see the code comment) — treat them as reversible. The result lands in the report as `detected_type`/`detected_confidence` and is shown in the GUI defect-panel header. Keep it free of pymeshlab/trimesh. Threshold resolution for BOTH the real repair and `--dry-run` goes through `repair.resolve_mode_params(mode, type, conf)` (returns `(params, tuning_applied)`), so they can never diverge.
- **Classifier engine selection (`repair.resolve_classifier_engine`).** The DEFAULT engine is `experimental` — `sutura/mesh_classifier_v2.py` (RANSAC plane features + a curvature developability signal + a trained numpy logistic head). Measured on the 40-mesh real-world corpus (36 labeled): experimental 29/36 vs classic 16/36 (mechanical recall 16/20 vs 2/20; organic 13/16 vs 14/16); LOO-CV on the 71-mesh labeled set (35 synthetic + 36 real) is 0.845 vs classic 0.648. The developability signal (`developable_fraction`, the area fraction whose normals lie on a common great circle) is what lets the head classify curved-but-mechanical parts (cylinders, tubes, fillets) that classic reads as `unknown`; the synthetic set gained `cylinder_*`, `tube_*`, `fillet_bracket` + damaged variants (now 35 meshes). `classic` (`mesh_classifier`) remains selectable via `--classifier-engine classic` / `SUTURA_CLASSIFIER_ENGINE=classic`. Precedence: CLI flag > env var > default (`experimental`); an invalid ENV value falls back to the default, an invalid CLI value is rejected by argparse. `repair.classify_with_engine` runs the selected engine and, on an exception/invalid result from `experimental`, SILENTLY falls back to classic with a stderr warning (never a crash) — `repair_mesh_from_arrays` reports the engine actually used as `classifier_engine`. **Near-boundary classic-agreement fallback (FAZ4):** the head's confidence is the margin from its 0.50 decision boundary, so `p_mech` near 0.5 is "no opinion" — the FAZ2-retrained head sat artec_metal-nut at p_mech=0.489 (conf 0.022, below ORG_TUNE_GATE), silently disabling organic tuning and dropping the 115-mesh corpus from 103 to 102 watertight. When `|p_mech - 0.5| * 2 < repair._HEAD_MARGIN` (0.15) AND classic strongly agrees with the barely-chosen class (`_classic_verdict` class == head class, classic class-score >= 0.70), the head keeps its class but reports classic's confidence, so the tuning gate sees the strong agreeing signal. Confident head decisions are NEVER overridden (no classic veto — that was tried and reverted as counterproductive). On the 115-mesh corpus this fallback fires on exactly ONE mesh (metal-nut); the near-boundary DISAGREEMENT cases (head coin-flip, classic strongly opposite: crankshaft, motorcycle-engine-cover-hd, plaster-cast-teeth) keep their low confidence → no tuning → conservative defaults, which is the intended "lean conservative" behaviour. **Eigenvalue shape descriptors evaluated, NOT integrated (FAZ6):** the Weinmann/Jutzi/Mallet (2015) point-set eigenvalue descriptors (Linearity/Planarity/Sphericity/Omnivariance/Anisotropy/Eigentropy/Surface Variation from the vertex-position 3x3 covariance) were implemented from the formulas in numpy and tested as extra head features. LOO-CV on the 71 labeled set gets WORSE (0.845 -> 0.831 with +linearity+sphericity, 0.817 with all 7; robust across floors 0.50-0.65): mechanical recall gains at most 1 while organic loses 2 — the global eigenvalue shape is largely redundant with the existing curvature/planarity features, so it was NOT integrated (the classifier is unchanged). **Local roughness/geometrical/statistical features as a tie-breaker, NOT integrated (FAZ8):** the IvanNik17 repo was re-read in full (roughness: GC roughness Wang 2012, DON Ioannou 2012, density Rabbani 2006, intensity entropy N/A for STL; geometrical: density/farthest/max-height/height-std Blomley-Weinmann 2016; statistical: D1-D4/A3) and reimplemented from scratch (1-ring vertex neighborhood, pure numpy); timzhang642/3D-Machine-Learning re-checked and confirmed as a link list, no code. Tested NOT as feature fusion but as a tie-breaker on the boundary/disagreement subset only (head conf < 0.5 or real-class disagreement): baseline 0.778 (27 meshes) -> 0.741, refined 0.643 (14) -> 0.429, per-feature |r| <= 0.36. Does not help, so NO --experimental-tiebreaker-features flag / GUI toggle was added and the classifier is unchanged. The source repo the ideas came from is GPL-3.0 (incompatible with Sutura's PolyForm Noncommercial license), so no code was copied — only the public formulas; the README "Classifier methodology" section documents the attribution and both negative results. Do not re-introduce these features without new evidence. **MeshCNN 5-D edge features evaluated as fusion AND tie-breaker, NOT integrated (FAZ9):** the MeshCNN per-edge feature (Hanoeka et al. 2019, MIT — reimplemented cleanly from the formula in numpy, no code copied) was implemented: for each interior edge, `dihedral = pi - arccos(n1.n2)`, sorted `symmetric_opposite_angles` (apex angle opposite the edge in each triangle) and sorted `symmetric_ratios` (apex-height/edge-length per triangle); 5 per-edge values -> 10 global mean/std stats (verified: cube dihedral mean ~2.09, smooth sphere ~2.97). Test A (fusion, LOO-CV on 71 labeled): base 0.845 -> base+10 edge features 0.831 (WORSE). Test B (tie-breaker on the FAZ8 boundary subset): union n=27 baseline 0.778 -> 0.741 (LOO, worse); refined n=14 baseline 0.643 -> 0.857 (LOO) but 3-fold x20 repeats give all-10 0.733 / best-3 0.902 — n=14 too small for "clear" evidence, best-3 has selection bias, union shows no help. Not a robust win -> NOT integrated (no --experimental-edge-features flag, no GUI toggle). NOTE the block-stacked edge indexing trap: the concatenated per-face edge array is [all (0,1) edges, then all (1,2), then all (2,0)] — use concatenate([arange(F),arange(F),arange(F)]) for edge->face, NOT repeat(arange(F),3) (same trap as mesh_classifier's i % F pairing). **Retrospective single-feature scan (FAZ10, project standing rule):** per-feature |correlation with the label| was computed on the FULL 71-set for all three rejected families — the top signals are REAL and above the n=71 noise bar (|r| < 0.4): `oppmax_std` (MeshCNN ratio-max std) r=+0.718, `don_mean` (DON) r=+0.673, `dihed_mean` (MeshCNN) r=-0.633, `rmin_mean` r=+0.563, `gc_mean` r=+0.480 — all sign-stable across 30 bootstrap subsamples (std ~0.04). However, added as a SINGLE feature the standalone LOO/5-fold-CV gain is marginal (<=+0.007 mean accuracy; deterministic LOO 0.845 -> 0.859 = 1 mesh; NO verdict flips in a final-model fit) — these strong correlates are largely REDUNDANT with the existing dihedral-based features (near90/flat/gentle + developable). None cleared the very-high standalone-integration bar; flagged as "interesting sub-pieces, revisit only via a proper feature-selection framework or with new data", NOT integrated. Standing rule: ALWAYS report per-feature |r| for rejected experiments, and flag any single feature with |r| > 0.4 that is consistent (full-set + bootstrap) for a separate standalone mini-evaluation. **Optional manifold3d cross-validation layer (FAZ10):** `sutura/manifold_bridge.watertight_check(verts, tris)` gives an independent manifold3d verdict (Manifold constructs with Error.NoError and is non-empty => watertight; open/non-manifold -> Error.NotManifold/empty). It sits NEXT TO defects.detect() strict watertight and never replaces it; integrated as an extra reporting column in `scripts/benchmark_repair_corpus.py` (`manifold3d_watertight`/`manifold3d_status`/`m3d_consistent`, reported as n/a when manifold3d is absent). manifold3d is an optional/heavy dependency (prebuilt wheels only up to Python 3.13; declared in requirements-311.txt + macOS conda env — NOT added to the Linux py3.14 requirements.txt, which documents why in a comment). Regression-tested by `tests/test_manifold3d_watertight.py`. **Opt-in edge-tiebreak head (FAZ11, `--experimental-edge-tiebreak`):** the five strongest FAZ10 scan signals (oppmax_std, don_mean, dihed_mean, rmin_mean, gc_mean) are NOT added to the default vector (LOO flips ~1 mesh, redundant with dihedral features). They are available as an OPT-IN 11-feature head (`V2_EXTRA_*` weights, `classify_mesh(extra_features=True)`, CLI flag threaded through `classify_with_engine`/`repair_mesh_from_arrays`/`process_file`; GUI batch-wide checkbox `chk_edge_tiebreak`). Trained on the 71 labeled set (LOO 0.845, 5-fold x20 0.852 vs base 0.850). **GUI FAZ11 features:** the interactive viewer gained a "defect colours" mode (red=non-manifold, orange=flipped, yellow=degenerate via `defects.defect_type_colors` -> npz `defect_colors` -> `heatmap.prepare_render(face_colors=...)`), and the main window gained a "What changed" repair-log panel (`_render_repair_log`, `_repair_log_by_path`). `mesh_classifier_v2.py` must stay in the module lists of `install.sh`, `install-macos.sh` and `scripts/build_appimage.sh` (it is imported only inside the experimental branch, so a missing file silently degrades every install to classic). The calibration harness `scripts/calibrate_classifier.py` defaults to `experimental` too.
- `sutura/autorefine.py` (numpy + pyrobust_predicates only, no pymeshlab/scipy/trimesh) is the experimental self-intersection resolution prototype (FAZ16) behind `--experimental-autorefine` (CLI + GUI batch-wide checkbox `chk_autorefine`): a from-scratch reimplementation of the Lazard & Valque 2025 loop — identify properly-intersecting triangle pairs (broad-phase grid hash + vectorized float64 prefilter + adaptive Shewchuk-style `orient3d`), snap-round the involved vertices and their cell-mates onto a float-exact grid, subdivide each triangle along its intersection segments (conforming: split points propagate to every triangle sharing the edge), round new vertices to the grid, iterate <=5 times with a faces-growth cap and a no-progress early stop. **It NEVER deletes an input face** (each triangle is kept or split), the property that targets the documented "extreme mode can worsen heavy-SI scans" failure mode. In `repair_mesh_from_arrays` the flag re-runs the same stage-1 chain on the autorefine-preprocessed input and **adopts it only when the final output has holes and non-manifold edges no worse than the baseline chain** (adopt/fallback guard); the report carries `experimental_autorefine` (si_before/si_after/iterations/converged/capped/adopted; `--human` shows an "Autorefine (experiment)" line). Exact predicates come from `pyrobust-predicates` (Unlicense/public-domain, pure-python wheel, deps mpmath) — added to requirements.txt and the macOS conda env; do NOT use the 2D-only `robust`/`shewchuk` packages. Measured on the 8 real-world SI targets: clear win on moderate-SI meshes (thingi10k_1038439 SI 411→97 standalone, 532→123 integrated vs chain-only; thingi10k_46012 224→168 integrated), NOT a win on dense-SI scans (1038441, metal-nut, 100281) where the float64 construction opens holes the chain cannot fully re-close — the documented EPICK limitation, which is why it stays flag-gated. `benchmark_repair_corpus.py` now records input/output SI (`input_self_intersections`/`output_self_intersections`/`stage1_si_remaining`) but the strict watertight metric deliberately still excludes SI. Keep `autorefine.py` in the module lists of `install.sh`, `install-macos.sh` and `scripts/build_appimage.sh`. The feasibility report and full before/after numbers are in `docs/alpha-wrap-feasibility-2026-09.md`.
- **FAZ16 refinement — iterative snap-rounding pass:** `autorefine.py`'s base loop gained the CGAL 6.1 (June 2025) second-half fix. After each snap, `_eliminate_degenerate` removes the degenerate/sliver/duplicate faces that snapping creates (never a whole non-degenerate input triangle), and `_iterative_snap_round` re-snaps + re-resolves the still-intersecting vertices iteratively (bounded by `MAX_SNAP_ROUNDS=8`, strict-decrease guard). The grid stays at the FINEST float-exact level (2^23) — coarsening it was measured on the heavy-SI corpus and rejected (100281: fine grid 906→97 pairs vs coarsened 906→74289; coarse grids amplify cell-mate snapping and manufacture new intersections). The report gained `snap_rounds_per_iteration`/`grid_scales_used`. Standalone pymeshlab-SI vs the pre-refinement autorefine: 100281 3677→4849→3787, 1038439 411→97→69, 46012 454→466→214. ## Conventions

- Input files are never overwritten — output always gets a `_fixed` suffix (or `-o`).
- Robustness is a hard requirement: truncated files, wrong-ext-mismatched content, NaN/Inf coordinates, empty/degenerate meshes must return a clear JSON `error` and exit 1, never a crash or a silent "clean" report.
- VCG chain lives in `stage1_chain`; `delete_fallback_chain` is tried only when the main chain leaves non-manifold edges/vertices, and is kept only if it improves them.

   `orcaslicer-plugin/` between this tag and the previous one and SKIPS the
   OrcaCloud publish step entirely if the plugin file did not change -- so a
   release with no plugin changes does not spam a new, unrelated Cloud
   version. No manual Cloud upload/paste step is needed anymore; do not
   revert to doing it by hand out of habit. If the plugin file DID change,
   verify after the fact that the new version actually appears on the Orca
   Cloud listing page (Actions tab -> workflow run -> check the "Publish
   release to OrcaCloud" step didn't get skipped and returned 2xx).

This checklist is the release process — steps 5 and 6 are not optional
extras to be reminded about separately; they are part of doing a release at
all.

General principle for this whole checklist: a command exiting 0 means
the command ran, not that its output is correct. For every step that
produces user-facing content (CHANGELOG entry, commit body, README
section, GitHub Release notes), read back what was actually written
before moving to the next step. This applies beyond releases too —
whenever a tool call's success is being used as evidence that content is
correct, verify the actual content instead of trusting the exit status.

## Cleanup discipline

- At the end of any session that created temporary/debug files (test scripts,
  probe files, generated meshes, log files used only for diagnosis), delete
  them without being asked — both in `/tmp` and in the repo. Before finishing,
  run `git status` and a quick `ls` of any temp working directories, and remove
  anything not meant to persist.

# AGENTS.md

Sutura: two-stage STL/3MF mesh repair for 3D printing. Stage 1 = PyMeshLab
(VCG filter chain), stage 2 = manifold3d solid rebuild. Git repo, branch
`main`, remote `Krateian/Sutura`.

Project goal: a fast and effective repair tool first, in the spirit of CGAL
and Netfabb. The default path stays simple and quick; the extras for advanced
users — the own exact geometry core (`rust/sutura-geom`), the own mesh-type
classifier, the opt-in experimental tiers — sit behind flags and the GUI's
Options window, never in the way of the plain repair.

## How it runs

- Real entry point is `sutura/repair.py` (JSON report to stdout; `--human` for a readable report; exit 0 on success or a stage-1-only partial, exit 1 on a hard error like malformed input). `bin/sutura` is only a bash wrapper: `exec $HOME/.local/share/sutura/venv/bin/python .../repair.py "$@"`. Two read-only modes share the same entry point: `sutura validate model.stl` (first positional arg `validate`) analyzes without repairing, and `sutura model.stl --dry-run` reports the would-do plan — both write NO output file. Mode/eşik resolution for repair AND dry-run comes from the shared `repair.resolve_mode_params(mode, type, conf)` (single source of truth, like classification.py).
- `repair.py` imports `pymeshlab` *inside* functions, not at module top, so running it with the plain system Python fails. It must run under the `~/.local/share/sutura/venv` interpreter (PyMeshLab), which talks to `venv311` (python3.11) for stage 2 via `sutura/manifold_bridge.py` as a subprocess.
- `install.sh` creates both virtualenvs (`venv` with PyMeshLab from `requirements.txt`, `venv311` with manifold3d from `requirements-311.txt`), installs the `sutura_geom` Rust extension via `scripts/install_sutura_geom.sh` (~0.7 MB prebuilt abi3 wheel from GitHub releases verified against `sutura_geom-SHA256SUMS`, or compiles from `rust/sutura-geom` if Rust is available; `SUTURA_NO_GEOM=1` opts out, `SUTURA_GEOM_FROM_SOURCE=1` forces source build), copies the source into `~/.local/share/sutura/`, and installs `~/.local/bin/sutura`. Re-running is safe. It bails if no `python3.11` is available (manifold3d ships wheels only up to Python 3.13).
- **AppImage build (alternative distribution):** `scripts/build_appimage.sh` bundles two relocatable python-build-standalone runtimes (Python 3.14 -> `usr/lib/sutura/venv`, Python 3.11 -> `usr/lib/sutura/venv311`) plus the `sutura_geom` extension and app modules and builds `dist/Sutura-x86_64.AppImage` with appimagetool (which carries its own `mksquashfs`, so no system package needed). The AppRun dispatch exports `SUTURA_DIR`/`SUTURA` so `repair.py` finds its venv311/bridge and `gui.py` finds its CLI without code changes. **AppImage mode detection:** `updater.py` checks the `APPIMAGE` env var (set by the AppImage runtime); in that mode the GUI skips the first-run ask / background checks and the update button shows a "download from releases" message instead of self-updating (self-update cannot write to a read-only squashfs). `updater.py`'s VERSION fallback reads `repair.py` beside itself before the host install dir so the bundled copy is authoritative.
- Multi-object 3MF files are repaired object-by-object in memory (numpy arrays), preserving the original archive structure. An object that stage 1 closes gets a **per-object stage 2** watertight rebuild through the shared `repair.maybe_run_stage2` helper (the same gate/OBJ round-trip as single-mesh files); per-object `stage2` reports, `objects_watertight`/`objects_stage2_ok` aggregates, and an ALL-objects file verdict (`classification._classify_objects`) were added in the same change that fixed the layered-mesh Stage-1 collapse. Single-mesh files round-trip through OBJ for stage 2. Byte-identical objects reuse one repair (geometry cache) but each still gets its own per-object report.
- Read-only analysis lives in `repair.validate_file` / `repair.dry_run_file` (per-mesh: `validate_mesh_from_arrays` / `dry_run_mesh_from_arrays`), both sharing `repair.load_meshes` (STL/OBJ via pymeshlab, 3MF via `parse_3mf_meshes`). `scan_bad_coordinates` skips `.3mf` (its XML parser silently drops non-numeric vertices) and is also the reason single-object 3MF repair works — do not make it treat 3MF as STL again.
- **Usage history (anonymous, opt-out):** `sutura/history.py` (stdlib+numpy, no pymeshlab) records a purely-technical repair log to `~/.local/share/sutura/history.jsonl` — mesh sizes, defect counts, classifier outcome, mode, category, confidence, timing + a quantized geometry `mesh_fingerprint` (sha256, for dedup). HARD RULE: never store file names/paths/users/IPs — `repair_file`/`repair_3mf` compute the fingerprint and stash it as a transient `report['_fp']` key; `process_file` always runs `history.pop_fingerprints(result)` (so `_fp` never leaks into the JSON stdout report) and, unless `--no-history`, `history.write(...)` (which swallows its own errors — recording never breaks a repair). validate/`--dry-run` never record. `sutura export-history` prints a summary + the full JSON array (one command; `--summary-only`/`--last N`/`--clear`). GUI: `updater.py` `DEFAULT_CONFIG['history_enabled']` (default true) drives the first-run dialog checkbox and `RepairWorker` adding `--no-history`. history.py must stay in the explicit module lists of `install.sh`, `install-macos.sh` and `scripts/build_appimage.sh`.
- The GUI (`sutura/gui.py`, PySide6) just shells out to the installed `sutura` CLI and parses the last stdout JSON line. The batch-wide `chk_*` checkboxes (fTetWild fallback + SI, autorefine, indirect autorefine, join components, edge tiebreak) are NOT laid out in the action row: they are re-parented unchanged into the non-modal `OptionsDialog` (`MainWindow._options_dialog`, created once in `_build_ui`; tabs General / Repair / Experimental / Updates / Changelog; opened by `btn_options`, Ctrl+, / Cmd+, and the update indicator, which opens the Updates tab); `_update_options_label` shows the count of options that differ from `_options_defaults`. A new batch-wide option goes into the matching tab (add it to `_options_defaults` too), not into the row. Any QThread the dialog starts (release notes) must never run on a headless Qt platform and is waited for in `MainWindow.closeEvent`. Its **Repair Mode** picker (a small "Mode: Auto" button next to the heatmap/before-after buttons) opens `RepairModeDialog`: a five-step horizontal QSlider (low/medium/auto/aggressive/extreme) with a live localized description and OK/Cancel. The mode is stored **batch-wide** on the MainWindow (`self._repair_mode`, default `auto`), not per file, and `RepairWorker` passes it to the CLI as `--mode <mode>`; the chosen mode must therefore be verified in the JSON `repair_mode` of the batch results, not in per-file state.
- Result classification lives in `sutura/classification.py` (stdlib-only, no numpy/pymeshlab): `classify()` returns `(category, issues, summary_key)` and both the CLI (`repair.py`) and the GUI (`gui.py`) import it so they never diverge. "Watertight" is only claimed when stage 2 actually ran and returned `ok`; a stage-1-closed mesh with stage 2 skipped/errored/never-run (e.g. macOS in-process fallback unavailable) is a warning. CLI `--human`/JSON label issues via this module (English, not localized); the GUI localizes the same codes through its EN/TR dictionary.
- `sutura/confidence.py` (stdlib-only) computes the repair confidence score: `repair_confidence()` (post-repair, category-anchored, stage 2 dominant, hard errors forced to 0/low) and `estimate_confidence_pre_repair()` (validate / `--dry-run` estimate, missing signals ignored). It lazy-imports the tuning gates from `repair.py` (`MECH_TUNE_GATE`/`ORG_TUNE_GATE`) so the score can never drift from the real repair thresholds; shared by the CLI and the GUI.
- `sutura/defects.py` (stdlib+numpy only) detects the input mesh's holes and non-manifold regions from plain `verts`/`tris` arrays; `repair.py` calls `detect()` on the input and stores it in the report's `defects` key (always in JSON; `--human` only with `--defects`). The GUI renders the selected file's defects in a panel below the log. Keep it free of pymeshlab/trimesh so it stays importable anywhere. `detect(..., with_indices=True)` additionally returns each defect's `verts_idx`/`faces_idx` index lists for the heatmap; the CLI uses the default (False) so its JSON contract is unchanged.
- `sutura/heatmap.py` (numpy + Qt QImage/QPainter only, no pymeshlab) is the defect heatmap rasterizer: it projects the mesh with an auto-fit orthographic isometric camera, depth-sorts faces (painter's algorithm) and fills each face red when it touches a defect vertex, grey otherwise (~250k tris/s on CPU). It is deliberately a **CPU rasterizer, not OpenGL**: offscreen GL draw calls (`glDrawArrays`/`glDrawElements`) segfault on headless systems (verified on an NVIDIA box without a display) and can be unavailable in the AppImage/macOS CI. Do not replace it with GL without re-checking that. `render(...)` also accepts an optional `frame=(center, scale)` from `shared_frame(verts_list, w, h, pad)` so several meshes can be rendered with the IDENTICAL camera (used by the before/after comparison), and `focus_frame(verts, verts_idx, w, h, pad, fill=0.75)` returns a zoomed frame centered on a defect region (its vertices' view-space bbox) for the before/after detail close-up.
- `sutura/heatmap_render.py` is a CLI entry run as a **subprocess** by the GUI's `HeatmapWorker` to load+detect+rasterise a heatmap into a PNG temp file. This isolation is required: using pymeshlab inside a Qt worker thread while a `QMainWindow` exists corrupts the heap at interpreter shutdown (PySide6 6.11 + Python 3.14). The GUI process therefore never imports pymeshlab. The GUI shows a "Show heatmap" button + clickable thumbnail (on-demand, cached per file; first object for multi-object 3MF) and falls back silently to the text-only panel on any failure.
- `sutura/before_after_render.py` is a second subprocess CLI entry (spawned by the GUI's `BeforeAfterWorker`) that loads the original AND repaired mesh, detects defects on BOTH, and writes FOUR PNGs: before (original defects red on grey), after (tri-state: grey = never broken, green `(46,204,113)` = healed, orange `(255,140,60)` = still broken), detail_before + detail_after (close-up of the WORST original defect region by physical bounding-box diagonal, both with the same zoomed frame from `heatmap.focus_frame`). **Camera: it is NOT the fixed isometric view** — the shared camera is directed toward the worst ORIGINAL defect's centroid via `heatmap.defect_camera(center, worst['centroid'])` so the defect never hides behind the mesh; the two-stage `shared_frame` call first yields the rotation-independent world-space bbox centre, then the real `(center, scale)` frame with that rotation so the scale fits R's view axes. `_ISOMETRIC` is used only when the mesh is clean or the defect sits at the bbox centre (R is None). Known limitation: on extremely asymmetric meshes (long/thin, dumbbell-like) the defect-facing angle can collapse the view-space bbox and render the mesh small — deferred to the v0.2 interactive 3D viewer (user-fixable), NOT improved now. Because repair changes topology (before/after indices differ), "healed" is a SPATIAL classification via `before_after_render.healed_face_mask(rverts, rtris, old_defects, overts, rep_defects, cap=256, halo=1.5)` (pure numpy, loops over defects / vectorizes over faces with buffer reuse): a repaired face is healed when it lies within 1.5× its real extent (max |v - centroid| from verts_idx, NOT diameter) of an original defect centroid and the repaired mesh's own detect() reports no defect there; only the `cap` largest defects drive the green highlight (still-broken orange is uncapped, full-resolution from rep_defects). `heatmap.render` gained an optional `healed=(M,)` mask + `healed_color` (default green) — defect faces win precedence; heatmap_render.py stays unchanged (backward compatible). No original defects -> detail mirrors the main views. The GUI's "Show before/after" button opens a dialog with the main image + a smaller detail close-up below it and ONE toggle button flipping both between Original/Repaired. Static CPU-rendered pair — NOT an interactive 3D slider, for the same GL-segfault reason as the heatmap.
- `sutura/viewer_common.py` is the shared pure-numpy+Qt helper module for the before/after comparison: `defect_vertex_set`, `broken_face_mask`, `healed_face_mask`, `defect_diagonal`, `worst_defect`, `initial_view_camera` (returns the defect-facing `rotation` + `(center, scale)` frame that BOTH the static and interactive views open with) plus the `ORANGE`/`GREEN`/`HEALED_CAP`/`HEALED_HALO` constants. It imports `heatmap` for the camera helpers; no pymeshlab. `before_after_render.py` re-exports these (its `healed_face_mask` is still the name `tests/test_healed_mask.py` imports), and `viewer_data_render.py` uses them directly.
- `sutura/viewer_data_render.py` is the LAZY subprocess CLI that builds the interactive-viewer dataset (spawned by the GUI's `ViewerDataWorker` the FIRST time the user picks "Interactive"; the npz is cached for the dialog's lifetime and dropped when the dialog closes — no persistent cache). It loads both meshes with pymeshlab, detects defects, computes healed masks, decimates each mesh to an interactive LOD (**`LOD_TARGET=3500`** via `meshing_decimation_clustering`; threshold steps `(0.5, 1.0, 2.0, 4.0, 8.0)`, closest-to-target wins), computes the surface-deviation distance with pymeshlab's `compute_scalar_by_distance_from_another_mesh_per_vertex` (measure=repaired, ref=original, `signeddist=False`; per-vertex unsigned nearest-surface distance — no scipy/rtree needed) plus `get_hausdorff_distance` for the global max, and writes ONE npz: full+LOD verts/tris for both meshes, `defect_vidx`/`broken_vidx` vertex lists, `healed`/`lhealed` masks, `distance`/`ldistance` arrays, `hausdorff`, the shared `frame_center`/`frame_scale`, `initial_rotation` (3x3, all-zero when the mesh is clean -> isometric fallback) and `viewport_w/h`. Regressed by `tests/test_viewer_data.py`. Measured on the 75-model corpus: the default `draw_frame` path at LOD 3500 gives median ~71 FPS, min 43.8 FPS, no model under 30 FPS (720x540).
- **Interactive viewer (v0.2).** `heatmap.render` is now a wrapper over `prepare_render` (one-time per mesh+mode: normals, lighting LUTs, defect/healed masks, deviation ramp -> a `RenderContext`) + `draw_frame(ctx, rotation, scale)` (per-frame: project + z-sort + QPainter) — byte-identical regression gate in `tests/test_heatmap.py`. A per-vertex `deviation` array drives the "surface deviation" view via `deviation_quantile_index` + `_deviation_lut` (navy->cyan->yellow->red, quantile-scaled); defect faces always win over the ramp. The GUI process renders interactively with `gui.py`'s `MeshViewport` (drag = yaw/pitch orbit via `_orbit_basis`, wheel = zoom `scale` override; LOD drawn during drag, ~300 ms idle -> full-res "final" frame) on a `_RenderThread` (latest-wins frame dropping, numpy+QPainter only — pymeshlab is NEVER in this thread or the GUI process). `_open_before_after` keeps the STATIC view as the default first view and adds a Static/Interactive radio switch; the interactive npz is built lazily and cached per dialog. Deviation mode only recolors the repaired side; still-broken faces stay orange on top; the Hausdorff max is shown as a label.
- `sutura/mesh_classifier.py` (stdlib+numpy only) heuristically classifies a mesh as `mechanical`/`organic`/`unknown` from dihedral-angle geometry. Its confidence is a **signed-margin score**: sigmoid memberships over three corrected dihedral bands (near90 `[60,120]°`, true-flat `<1°`, gentle-curvature `[1,15)°`; mechanical = max/OR of near90 & flat signals, organic = min/AND of low near90, low flat, high gentle), decisions at fixed floors (`mechanical >= 0.7`, `organic >= 0.5`), and `unknown` carries a non-zero proximity value + `metrics['leaning']` instead of a flat 0. NOTE: the edge→face pairing uses `i % F` (the concatenated edge array is block-stacked, not per-face); the old `i // 3` paired up unrelated faces and produced garbage near90/coplanar — the old `coplanar` metric was replaced by the `flat`/`gentle` split precisely so smooth high-poly organics (dihedrals ~2-5°, i.e. `gentle`) never read mechanical. `repair_mesh_from_arrays` calls it and, on non-`unknown`, tunes two Stage 1 thresholds (`mincomponentsize`, `maxholesize`) via the module-level `_TYPE_PARAMS` table in `repair.py` — but only when confidence clears the **class-specific tuning gate** (`repair.MECH_TUNE_GATE=0.75`, `repair.ORG_TUNE_GATE=0.70`, helper `repair.tuning_applied_for`): below the gate the detected type is still reported but the conservative default thresholds are used, and the report carries `tuning_applied` (true/false; shown in `--human` and the GUI defect panel). Both gates sit just above the worst correct prediction on the corrected set (mechanical min 0.867, organic min 0.693) — the old `0.55` organic gate and its "structurally capped at ~0.62" rationale were artifacts of the pairing bug. Those per-type values are EXPERIMENTAL/uncalibrated starting points (see the code comment) — treat them as reversible. The result lands in the report as `detected_type`/`detected_confidence` and is shown in the GUI defect-panel header. Keep it free of pymeshlab/trimesh. Threshold resolution for BOTH the real repair and `--dry-run` goes through `repair.resolve_mode_params(mode, type, conf)` (returns `(params, tuning_applied)`), so they can never diverge.
- **Classifier engine selection (`repair.resolve_classifier_engine`).** The DEFAULT engine is `experimental` — `sutura/mesh_classifier_v2.py` (RANSAC plane features + a curvature developability signal + a trained numpy logistic head). Measured on the 40-mesh real-world corpus (36 labeled): experimental 29/36 vs classic 16/36 (mechanical recall 16/20 vs 2/20; organic 13/16 vs 14/16); LOO-CV on the 71-mesh labeled set (35 synthetic + 36 real) is 0.845 vs classic 0.648. The developability signal (`developable_fraction`, the area fraction whose normals lie on a common great circle) is what lets the head classify curved-but-mechanical parts (cylinders, tubes, fillets) that classic reads as `unknown`; the synthetic set gained `cylinder_*`, `tube_*`, `fillet_bracket` + damaged variants (now 35 meshes). `classic` (`mesh_classifier`) remains selectable via `--classifier-engine classic` / `SUTURA_CLASSIFIER_ENGINE=classic`. Precedence: CLI flag > env var > default (`experimental`); an invalid ENV value falls back to the default, an invalid CLI value is rejected by argparse. `repair.classify_with_engine` runs the selected engine and, on an exception/invalid result from `experimental`, SILENTLY falls back to classic with a stderr warning (never a crash) — `repair_mesh_from_arrays` reports the engine actually used as `classifier_engine`. **Near-boundary classic-agreement fallback (FAZ4):** the head's confidence is the margin from its 0.50 decision boundary, so `p_mech` near 0.5 is "no opinion" — the FAZ2-retrained head sat artec_metal-nut at p_mech=0.489 (conf 0.022, below ORG_TUNE_GATE), silently disabling organic tuning and dropping the 115-mesh corpus from 103 to 102 watertight. When `|p_mech - 0.5| * 2 < repair._HEAD_MARGIN` (0.15) AND classic strongly agrees with the barely-chosen class (`_classic_verdict` class == head class, classic class-score >= 0.70), the head keeps its class but reports classic's confidence, so the tuning gate sees the strong agreeing signal. Confident head decisions are NEVER overridden (no classic veto — that was tried and reverted as counterproductive). On the 115-mesh corpus this fallback fires on exactly ONE mesh (metal-nut); the near-boundary DISAGREEMENT cases (head coin-flip, classic strongly opposite: crankshaft, motorcycle-engine-cover-hd, plaster-cast-teeth) keep their low confidence → no tuning → conservative defaults, which is the intended "lean conservative" behaviour. **Eigenvalue shape descriptors evaluated, NOT integrated (FAZ6):** the Weinmann/Jutzi/Mallet (2015) point-set eigenvalue descriptors (Linearity/Planarity/Sphericity/Omnivariance/Anisotropy/Eigentropy/Surface Variation from the vertex-position 3x3 covariance) were implemented from the formulas in numpy and tested as extra head features. LOO-CV on the 71 labeled set gets WORSE (0.845 -> 0.831 with +linearity+sphericity, 0.817 with all 7; robust across floors 0.50-0.65): mechanical recall gains at most 1 while organic loses 2 — the global eigenvalue shape is largely redundant with the existing curvature/planarity features, so it was NOT integrated (the classifier is unchanged). **Local roughness/geometrical/statistical features as a tie-breaker, NOT integrated (FAZ8):** the IvanNik17 repo was re-read in full (roughness: GC roughness Wang 2012, DON Ioannou 2012, density Rabbani 2006, intensity entropy N/A for STL; geometrical: density/farthest/max-height/height-std Blomley-Weinmann 2016; statistical: D1-D4/A3) and reimplemented from scratch (1-ring vertex neighborhood, pure numpy); timzhang642/3D-Machine-Learning re-checked and confirmed as a link list, no code. Tested NOT as feature fusion but as a tie-breaker on the boundary/disagreement subset only (head conf < 0.5 or real-class disagreement): baseline 0.778 (27 meshes) -> 0.741, refined 0.643 (14) -> 0.429, per-feature |r| <= 0.36. Does not help, so NO --experimental-tiebreaker-features flag / GUI toggle was added and the classifier is unchanged. The source repo the ideas came from is GPL-3.0 (incompatible with Sutura's PolyForm Noncommercial license), so no code was copied — only the public formulas; the README "Classifier methodology" section documents the attribution and both negative results. Do not re-introduce these features without new evidence. **MeshCNN 5-D edge features evaluated as fusion AND tie-breaker, NOT integrated (FAZ9):** the MeshCNN per-edge feature (Hanoeka et al. 2019, MIT — reimplemented cleanly from the formula in numpy, no code copied) was implemented: for each interior edge, `dihedral = pi - arccos(n1.n2)`, sorted `symmetric_opposite_angles` (apex angle opposite the edge in each triangle) and sorted `symmetric_ratios` (apex-height/edge-length per triangle); 5 per-edge values -> 10 global mean/std stats (verified: cube dihedral mean ~2.09, smooth sphere ~2.97). Test A (fusion, LOO-CV on 71 labeled): base 0.845 -> base+10 edge features 0.831 (WORSE). Test B (tie-breaker on the FAZ8 boundary subset): union n=27 baseline 0.778 -> 0.741 (LOO, worse); refined n=14 baseline 0.643 -> 0.857 (LOO) but 3-fold x20 repeats give all-10 0.733 / best-3 0.902 — n=14 too small for "clear" evidence, best-3 has selection bias, union shows no help. Not a robust win -> NOT integrated (no --experimental-edge-features flag, no GUI toggle). NOTE the block-stacked edge indexing trap: the concatenated per-face edge array is [all (0,1) edges, then all (1,2), then all (2,0)] — use concatenate([arange(F),arange(F),arange(F)]) for edge->face, NOT repeat(arange(F),3) (same trap as mesh_classifier's i % F pairing). **Retrospective single-feature scan (FAZ10, project standing rule):** per-feature |correlation with the label| was computed on the FULL 71-set for all three rejected families — the top signals are REAL and above the n=71 noise bar (|r| < 0.4): `oppmax_std` (MeshCNN ratio-max std) r=+0.718, `don_mean` (DON) r=+0.673, `dihed_mean` (MeshCNN) r=-0.633, `rmin_mean` r=+0.563, `gc_mean` r=+0.480 — all sign-stable across 30 bootstrap subsamples (std ~0.04). However, added as a SINGLE feature the standalone LOO/5-fold-CV gain is marginal (<=+0.007 mean accuracy; deterministic LOO 0.845 -> 0.859 = 1 mesh; NO verdict flips in a final-model fit) — these strong correlates are largely REDUNDANT with the existing dihedral-based features (near90/flat/gentle + developable). None cleared the very-high standalone-integration bar; flagged as "interesting sub-pieces, revisit only via a proper feature-selection framework or with new data", NOT integrated. Standing rule: ALWAYS report per-feature |r| for rejected experiments, and flag any single feature with |r| > 0.4 that is consistent (full-set + bootstrap) for a separate standalone mini-evaluation. **Optional manifold3d cross-validation layer (FAZ10):** `sutura/manifold_bridge.watertight_check(verts, tris)` gives an independent manifold3d verdict (Manifold constructs with Error.NoError and is non-empty => watertight; open/non-manifold -> Error.NotManifold/empty). It sits NEXT TO defects.detect() strict watertight and never replaces it; integrated as an extra reporting column in `scripts/benchmark_repair_corpus.py` (`manifold3d_watertight`/`manifold3d_status`/`m3d_consistent`, reported as n/a when manifold3d is absent). manifold3d is an optional/heavy dependency (prebuilt wheels only up to Python 3.13; declared in requirements-311.txt + macOS conda env — NOT added to the Linux py3.14 requirements.txt, which documents why in a comment). Regression-tested by `tests/test_manifold3d_watertight.py`. **Opt-in edge-tiebreak head (FAZ11, `--experimental-edge-tiebreak`):** the five strongest FAZ10 scan signals (oppmax_std, don_mean, dihed_mean, rmin_mean, gc_mean) are NOT added to the default vector (LOO flips ~1 mesh, redundant with dihedral features). They are available as an OPT-IN 11-feature head (`V2_EXTRA_*` weights, `classify_mesh(extra_features=True)`, CLI flag threaded through `classify_with_engine`/`repair_mesh_from_arrays`/`process_file`; GUI batch-wide checkbox `chk_edge_tiebreak`). Trained on the 71 labeled set (LOO 0.845, 5-fold x20 0.852 vs base 0.850). **GUI FAZ11 features:** the interactive viewer gained a "defect colours" mode (red=non-manifold, orange=flipped, yellow=degenerate via `defects.defect_type_colors` -> npz `defect_colors` -> `heatmap.prepare_render(face_colors=...)`), and the main window gained a "What changed" repair-log panel (`_render_repair_log`, `_repair_log_by_path`). `mesh_classifier_v2.py` must stay in the module lists of `install.sh`, `install-macos.sh` and `scripts/build_appimage.sh` (it is imported only inside the experimental branch, so a missing file silently degrades every install to classic). The calibration harness `scripts/calibrate_classifier.py` defaults to `experimental` too.
- `sutura/autorefine.py` (numpy + pyrobust_predicates only, no pymeshlab/scipy/trimesh) is the experimental self-intersection resolution prototype (FAZ16) behind `--experimental-autorefine` (CLI + GUI batch-wide checkbox `chk_autorefine`): a from-scratch reimplementation of the Lazard & Valque 2025 loop — identify properly-intersecting triangle pairs (broad-phase grid hash + vectorized float64 prefilter + adaptive Shewchuk-style `orient3d`), snap-round the involved vertices and their cell-mates onto a float-exact grid, subdivide each triangle along its intersection segments (conforming: split points propagate to every triangle sharing the edge), round new vertices to the grid, iterate <=5 times with a faces-growth cap and a no-progress early stop. **It NEVER deletes an input face** (each triangle is kept or split), the property that targets the documented "extreme mode can worsen heavy-SI scans" failure mode. In `repair_mesh_from_arrays` the flag re-runs the same stage-1 chain on the autorefine-preprocessed input and **adopts it only when the final output has holes and non-manifold edges no worse than the baseline chain** (adopt/fallback guard); the report carries `experimental_autorefine` (si_before/si_after/iterations/converged/capped/adopted; `--human` shows an "Autorefine (experiment)" line). Exact predicates come from `pyrobust-predicates` (Unlicense/public-domain, pure-python wheel, deps mpmath) — added to requirements.txt and the macOS conda env; do NOT use the 2D-only `robust`/`shewchuk` packages. - **Rust morphology core — `rust/sutura-geom` (F2):** new modules independent of the exact-arrangement path. `src/winding.rs` builds a triangle BVH and evaluates the generalized winding number (Barill et al. 2018: exact triangle solid angle for near nodes, dipole far-field for nodes subtending less than `WINDING_FAR_TOL=1e-2` sr) plus branch-and-bound closest-point unsigned distance; signed distance is `sign(w-0.5)*unsigned`; grid queries are rayon-parallel (`rayon = "1.12"`, pure Rust, ~1.1 MB source, MIT/Apache-2.0 — the only new dependency). `src/morph.rs` implements the Felzenszwalb–Huttenlocher exact separable EDT and closing as dilate (`sdf-r`) → true EDT re-distance of the dilated occupancy (so erosion does not cancel the dilation) → erode (`+r`), plus a boundary flood-fill `fill_cavities`. `src/dual_contour.rs` is manifold dual contouring: one Hermite QEF vertex per cell surface component (Tikhonov-regularised symmetric 3x3 eigen-solve, clamped to the cell), quads over sign-change grid edges, and a marching-tetrahedra fallback if the manifold check fails. The Python API is `sutura_geom.sdf_grid(verts, tris, voxel=None, box=None)` and `sutura_geom.morph_close(verts, tris, r, voxel=None, box=None, fill_cavities=False)`; grids cap at `MAX_VOXELS=512^3` with automatic coarsening and accept a sub-`box` window. `r == 0` is accepted as the **sign-field path**: `close_sdf` (and the dilation padding) is skipped and the raw signed field feeds dual contouring directly, so gaps stay open; `info['sign_field']` records the mode and the module exports `SIGN_FIELD_SUPPORTED` so callers can feature-detect it. - **Rust ray-stabbing inside/outside vote — `rust/sutura-geom` (`src/raycast.rs`, experimental):** a Nooruddin & Turk (2003) "spray" vote used to disambiguate the generalized-winding sign in the ambiguous band `0.3 < w < 0.7`, where the field alone cannot decide (overlapping unioned shells, inconsistently oriented soups). `winding.rs` gained exact ray casting (`MeshBvh::intersect_ray` -> `RayQuery {net, crossings, nearest_t, suspect}`; `ray_node` traversal ignores the dipole far-field shortcut; `ray_tri_hit` is f64 Möller–Trumbore with sign `sign(dot(dir, n))`, grazing hits flagged, shared-edge hits deduplicated within `1e-6*diag`). The vote is the **oriented net crossing sum** `Σ sign(dot(dir, n_face))` (`> 0` inside; correct union/cavity semantics and reduces to parity for a single consistent shell), with each ray falling back to crossing parity when `net < 0` or `(net == 0 and odd)`; `parity=True` forces parity for all rays. An escaping ray (zero hits) is an outside vote weighted `escape_weight=2.0`. `Stabber` (default `DEFAULT_DIRS=13` jittered Fibonacci directions, clamped `MIN_DIRS=3`..`MAX_DIRS=26`) + `disambiguate_sdf(...)` patch only ambiguous-band cells, parallel over z-slices, leaving unresolved votes (majority grazing/suspect) to the winding number; `cells_flipped` is computed from the SIGNED slice's previous sign (not the unsigned distance, which is always `>= 0`, so the counter used to count inside votes instead of flips). Python API: `raystab_points(verts, tris, points, n_dirs=None, seed=0, parity=False, escape_weight=2.0) -> (inside, inside_votes, outside_votes, escape_votes)`, `raystab_grid(...) -> (inside, score, info)`, and an opt-in `raystab=` keyword on `sdf_grid`/`morph_close` (`raystab_dirs`/`raystab_seed`/`raystab_parity`); kwargs are APPENDED after `surface` so Graft's positional call keeps working. It is OFF by default and byte-identical to the winding-only path; `info['raystab']`/`report['raystab']` is only set when on. `sutura_engine/cast.py` wraps both functions and `graft.py` exposes `shell_wrap(..., raystab=..., raystab_dirs=..., raystab_seed=..., raystab_parity=...)` plus the `SUTURA_RAYSTAB` env opt-in (feature-detected so an older extension degrades to off). CLI/GUI wiring is deliberately DEFERRED until a real-world-corpus measurement (see `docs/cli-gui-parity-notes.md`). Regression: the `raycast`/`winding` Rust unit tests and `tests/test_raystab.py`.

- **Dressing (#16, variable-viscosity volumetric skinning) — `sutura_engine/dressing.py`, opt-in.** The surgical sibling of Graft: the input is dipped in a spatially varying "liquid" and the `F(x) = s(x) - r(x)` level set is extracted, where `s` is the generalized-winding signed distance (`sutura_geom.sdf_grid`) and `r(x) = r_base + (r_max - r_base) * exp(-d_defect^2 / 2 sigma^2)` a viscosity radius that is thin over detailed healthy surface and thicker over damage (`d_defect` = scipy EDT of the hole / non-manifold / self-intersecting vertex mask). The isosurface of a scalar field is 2-manifold and self-intersection-free by construction; because projecting the coat back onto the input surface re-introduced 7,850 SI faces (measured on framebaroque and permanently rejected), fidelity comes from a thin `r_base` instead. Pure API `dressing_coat(verts, tris, *, voxel=None, intensity=None, grid_budget=None, r_base=None, r_max=None, sigma=None, ml=None, guard=True, time_budget=None, drain=None, defects=None, r_max_scale=None, sigma_scale=None) -> (v, t, report)` (`report['display_name']='Dressing'`, `invents_geometry=True`). `defects` selects the input defect set driving the viscosity mask (`DRESSING_DEFECT_SETS = ('all', 'holes_nm')`; `all` = holes + non-manifold + self-intersections, `holes_nm` = holes + non-manifold only), and `r_max_scale` / `sigma_scale` multiply the resolved `r_max` / `sigma` (None = 1.0; non-positive / unparseable values are ignored by `resolve_dressing_rmax_scale` / `resolve_dressing_sigma_scale`). All three land in `report['defects']` / `report['r_max_scale']` / `report['sigma_scale']` and are threaded through `repair.dressing_tier` / `repair.deep_repair_ladder` / `repair_mesh_from_arrays` / `repair_file` / `repair_3mf` / `process_file`; the CLI flags are `--dressing-defects {all,holes_nm}` / `--dressing-rmax-scale F` / `--dressing-sigma-scale F` (`SUTURA_DRESSING_DEFECTS` / `SUTURA_DRESSING_RMAX_SCALE` / `SUTURA_DRESSING_SIGMA_SCALE`). **Voxel = the feature anchor** (`_median_edge_length / 1.5`), clipped to the intensity preset's diagonal band (`DRESSING_BY_INTENSITY`: quick 120-200, balanced 200-350, thorough 300-500, extreme 450-800) with a small-model brake (`< 500` faces skips the fine end) and grid-budget coarsening; this fixes the thingi10k_100827 7.3 % oversampling (it was evaluated at `diag/200`). Viscosity defaults `r_base = clip(0.3*ell, 0.25*voxel, 0.8*voxel)`, `r_max = min(r_preset, 3.5*ell, 0.45*gap)`, `sigma = max(2*ell, 2*voxel)`. **Extraction** is a numpy marching-tetrahedra port of the prototype (`mt.py`, per-triangle edge grouping + positional weld) with a BFS face re-orientation + positive-volume flip; the Rust `sutura_geom.dressing_coat` (narrow-band field + coat extractor, `feat/dressing` c2f2116) is feature-detected via `_rust_dressing_coat` and used when present (`report['engine']='rust'/'numpy'`, `info` carries `band`/`band_cells`/`field_seconds`/`manifold`), falling back to numpy on any error. The Rust binding is `dressing_coat(verts, tris, defect_pts=None, voxel=None, r_base=None, r_max=None, sigma=None, band_voxels=2.0, margin_voxels=3.0, drain=0.0)` — `defect_pts` is an **Nx3 point array** (the Python layer converts its defect vertex indices) and `drain` carries the healthy-region erode-back `delta_r`; the Python layer feature-detects the parameter via `_rust_signature_has_drain` (introspection + a keyword probe) and falls back to the numpy path for a positive drain when the installed extension predates it. The reported `defects` / `r_max_scale` / `sigma_scale` are resolved in the Python layer before dispatch, so they apply to both engines. **Decimation** (`_decimate_coat`, target `max(min(F_in, 500k), 50k)`) uses `meshing_decimation_quadric_edge_collapse` with `optimalplacement=False` + `planarquadric=True` (0 SI, sub-micron fidelity, ~20 s per the decimation benchmark; the report recommends `min(N_input, 400k)`, and a 2-step schedule runs when the target <= half the raw coat) and rolls back atomically to the un-decimated coat on any holes / non-manifold / exact-SI violation. **Component cleanup (`_clean_coat_components`, before decimation):** the extracted triangle soup is split into vertex-connected components (scipy sparse connected-components) and the extraction debris — a component below `CLEANUP_MIN_FACES=64` OR `CLEANUP_ABS_VOXELS=32 * voxel^3` OR `CLEANUP_REL_VOLUME=1e-3 * largest|vol|` (thresholds measured on the 145065/63785/1038439 coats: debris <= 932 faces / ~0.6 voxel^3, smallest genuine shell 10 176 faces / ~5 000 voxel^3) — is dropped; a surviving inverted component is kept only when it is nested (bbox) inside a kept positive component AND the input's generalized winding number (`PyMeshBvh.winding_points`, built over `v0`/`t0`) at its centre is `< 0.5`, i.e. the input is genuinely empty there (a true cavity, e.g. a hollow-shell input). Positive components must also overlap the input bbox. It never raises (`ran=False` on any failure), is a byte-identical no-op for a single-component coat, and falls back to the untouched coat if it would remove all geometry; `report['cleanup']` (surfaced by `repair.dressing_tier` as `report['dressing']['cleanup']`) carries `components_before/after`, `kept_positive/kept_cavities`, `removed_debris/negative/other`, `removed_faces/volume` and the thresholds. Measured on the 13-mesh `dressing_tuned` set (2026-10): 145065 669 -> 1, 63785 25 -> 1 (both OrcaSlicer `number_of_parts` 1 after), framebaroque 8 -> 1; 1038439 keeps its 3 genuine material lumps (its input Orca `number_of_parts = 6`, so the remaining `number_of_parts = 3` is an input property, not a Dressing failure). **SI cap caveat:** the exact classifier only verifies at <= `SI_MAX_FACES` (150k today), so `si_after=None` above that reads as "unknown" and adoption accepts it; once the Rust cap is raised the same `_exact_si` call verifies the coat with no code change. **Drain ("erode-back", `dressing_coat(drain=...)`, `_resolve_drain`):** the coat sits ~`r_base` OUTSIDE the original (dimension growth); the drain is applied **in the level set** (`F = s - r + delta_r`, `_numpy_coat`/`_rust_dressing_coat`), NEVER by vertex projection (which re-introduced 7,850 SI and is permanently rejected). `drain=None` uses the preset's `drain_factor` (`DRESSING_BY_INTENSITY`: quick 0.0 off, balanced/thorough 1.0 full, extreme 1.25 deep per the offset report), and the argument also accepts a mode name (`none`/`half`/`full`/`deep` in `DRAIN_MODES`) or an explicit `delta_r` in mm. Full drain reduces healthy growth ~40 % (median +0.33 -> +0.20 mm raw) with a ~4 um median inward dip and keeps defects covered; `report['drain']={'mode','factor','delta_r','amount','drained'}`. Resolution: `repair.resolve_dressing_drain` (`--dressing-drain MODE|mm` > `SUTURA_DRESSING_DRAIN` > None). **Known residual:** a ~0.2 mm (~0.4 voxel at 0.5 mm) outward bias remains even at full drain — the extractor's discretization, to be addressed in the Rust core, NOT hidden with vertex projection. **Adoption** (`repair.dressing_tier`): strict reload-watertight AND `si_after in (0, None)` AND `report['fidelity_ok']` (coat->input max deviation below the preset gate: 1.5/0.8/0.4/0.25 % of the diagonal) AND three shape-preservation gates against the result the ladder held before Dressing — signed-volume delta `<= repair.DRESSING_MAX_VOLUME_DELTA` (0.10), component-count growth `<= repair.DRESSING_MAX_PARTS_SLACK` (1) and healthy-surface P95 coat-vs-input **vertex-normal** angle `< repair.DRESSING_MAX_NORMAL_ANGLE_P95` (30 deg, PLACEHOLDER; measured Dressing p95 is 12-36 deg on the accepted 13-mesh coats and 82-88 deg on framebaroque / 100281 / 1038439 / 1038441 / 145065). The normal metric is `dressing.normal_angle_deviation(wv, wt, v0, t0, defect_idx)` (nearest input vertex via a scipy `cKDTree`, healthy = nearest input vertex not in `defect_idx`, returns p50/p95/p99/max/n; `None` without scipy) with `_vertex_normals`; the helpers `dressing.si_face_count` / `signed_volume` / `count_components` sit beside it, and `dressing_coat` reports `normal_angle_p*` / `components_after` / `volume_after`. `repair.cad_likeness(verts, tris)` returns `{'score','planar_fraction','sharp_fraction','cad_like'}` (flat edge < 1 deg, sharp > 30 deg, score = max; cube 0.667 cad_like=True, sphere 0.0 False) and is recorded in `report['deep_repair']['cad_likeness']` on every Auto run — the CAD guard hook (the ladder runs Graft first for ALL inputs, so a CAD-like part already gets the verbatim Graft hybrid before Dressing); the calibrated detector will drive the ordering. The candidate is then confirmed by stage 2 at the top level. `classification.classify` adds the `dressing_detail_loss` issue only for an *adopted* Dressing with warnings (never changes the category). `report['dressing']` carries the parameters, deviations, exact-SI verdict, EN/TR warnings and time budget; `--human` prints a `Dressing (viscosity)` line. **Auto-ladder fallback behind a single default switch, shipped OFF.** The lib default `repair_mesh_from_arrays(dressing=False)` is unchanged; `repair.resolve_dressing(no_dressing, force, environ, default_enabled)` returns `False` / `True` (forced) / `'auto'` (fallback). ## Sutura Engine Architecture (`sutura_engine`)

The core repair functionality is organized under `sutura/sutura_engine/`. Installed and AppImage layouts copy it to a top-level `sutura_engine` package; in a source checkout the repo-root `sutura_engine/__init__.py` bootstrap provides `import sutura_engine` (and `import sutura_engine.<submodule>`) from the repository root, replacing the former root symlink (symlinks are not portable across AppImage, zip archives and Windows). The bootstrap only adds `sutura/` to `sys.path` and points `__path__` at `sutura/sutura_engine`; PyInstaller leaves that explicit `__path__` untouched (`--hidden-import sutura_engine` + `--collect-submodules` still resolve the real package because `--paths sutura` is in the spec). The engine enforces strict layer separation, lazy third-party imports, content-addressed caching, and a pluggable method registry:

- `sutura_engine.core`: Generic low-level mesh I/O (STL, OBJ, 3MF arrays), geometric validation, and Hausdorff distance computations. Re-exports the specialised passes below for backward compatibility.
- `sutura_engine.diagnosis`: Object feature analysis (`analyze_mesh`/`analyze_file`, `ObjectAnalysis`), geometric template matching (`Template`, `SCORE_TEMPLATES`), and classifier glue (`classify_with_engine`).
- `sutura_engine.chart`: Content-addressed cache located in `~/.cache/sutura/`. Keys are SHA-256 hashes of input mesh arrays + engine version + parameters. Enforces a 500 MB LRU size limit, auto-invalidates on version change, and supports `--no-cache` CLI flag and GUI Options toggle/button.
- `sutura_engine.stitch`: Reload-safe seam healing pass (P-WELD: `p_weld_final`, `_separate_weld_collisions`), split out of `core`.
- `sutura_engine.xray`: Reload-honest strict watertight verdict (P-HONEST: `weld_reload_equivalent`, `reload_strict_holes_nm`, `enforce_reload_verdict`), split out of `core`.
- `sutura_engine.hull`: Outer-surface shell extraction (`extract_outer_shell`).
- `sutura_engine.cast`: Thin wrapper around the Rust `sutura_geom` extension (exact `orient3d`/`insphere`, `arrangement_lite`).
- `sutura_engine.mirror`: Mirror-plane completion for single-sided scans (method #14): `detect_mirror_plane` / `mirror_close` (reflect, weld, `extract_outer_shell`, Poisson fallback). `sutura/mirror_repair.py` re-exports it.
- `sutura_engine.wall`: Thin-wall analysis and thicken-to-min (method #15): `build_sdf_grid`, `estimate_wall_thickness`, `thicken_to_min` (morphological dilation + marching-tetrahedra extraction). `sutura/wall_thickness.py` re-exports it.
- `sutura_engine.dressing`: Variable-viscosity volumetric skinning (method #16, opt-in): `dressing_coat` extracts the `F(x) = s(x) - r(x)` level set of the generalized-winding signed field (`sdf_grid` -> variable radius -> marching tetrahedra -> decimation with rollback -> P-WELD), feature-detects and delegates to the Rust `sutura_geom.dressing_coat` when present. Re-exported by the legacy `sutura/shell_wrap.py`? No: it is imported by `repair.dressing_tier` via `sutura_engine.dressing` directly (no top-level shim).
- `sutura_engine.learning`: Learning-triage aggregation and the bounded ranking bonus (`record_learning`, `triage_stats`, `learning_bonus`, `clear_learning`, `learning_enabled`). `sutura/history.py` re-exports it (the usage-history store itself stays top-level).
- `sutura_engine.methods`: Pluggable repair method registry conforming to `RepairMethodProtocol`. Built-in methods live in `sutura_engine/methods/builtin/` as one named module per method (see the naming table below) and are auto-discovered on import. Special tiers (closing, proxy, repeat, P-WELD) are modularized here.
- `sutura_engine.triage`: Budget-aware auto-escalation policy (`repair_with_methods`, `_auto`, `_auto_multi`), intensity profiles (`quick`, `balanced`, `thorough`, `extreme`), and per-object 3MF escalation loops. Triage remains strictly stdlib-only on import.
- `sutura_engine.adapters`: Strict boundaries around third-party libraries:
  - `pymeshlab_adapter`: Stage 1 VCG repair filter chains (lazy import, never imported at engine top-level).
  - `manifold_adapter`: Manifold3d in-process execution and subprocess bridge dispatch (`manifold_bridge.py`, `csg_bridge.py`).
  - `ftetwild_adapter`: fTetWild tetrahedralization fallback tier and status checks.
  - `external_adapter`: User-configured external CLI repair engines (`~/.config/sutura/engines/*.toml`).
- Public Python API: `sutura_engine.repair(path_or_arrays, methods=None, intensity=..., ...) -> Report`.
- Backward Compatibility: Shims exist at the previous engine paths   (`sutura_engine/analysis.py` -> `diagnosis`, `sutura_engine/cache.py` -> `chart`) and the legacy top-level modules (`closing.py`, `proxy_repair.py`, `repeat_repair.py`, `mirror_repair.py` -> `sutura_engine.mirror`, `wall_thickness.py` -> `sutura_engine.wall`, `object_analysis.py`, `templates.py`, `engines.py`, `methods.py`, `triage.py`) re-export from `sutura_engine`. `history.py` is a real top-level module but re-exports the learning-triage API from `sutura_engine.learning`.

## How to add a repair method

Sutura's repair engine is designed to be easily extensible. Any new repair method can be added without modifying the core pipeline or triage logic.

### 1. Implement `RepairMethodProtocol`
A repair method is a callable class or object conforming to `RepairMethodProtocol` (defined in `sutura_engine.methods.protocol`):
```python
from dataclasses import dataclass, field
from typing import Optional, Tuple
import numpy as np
from sutura_engine.methods.protocol import (
    RepairContext, MethodResult, RepairMethod
)

@dataclass(frozen=True)
class MyCustomMethod(RepairMethod):
    num: int = 16
    id: str = "my_custom"
    name: str = "My Custom"
    display_name: str = "My Custom Repair"
    description: str = "Repairs custom defects using specialised algorithms."
    family: str = "custom"
    invents_geometry: bool = False

    def available(self) -> Tuple[bool, Optional[str]]:
        """Return (is_available, failure_reason)."""
        return True, None

    def repair(self, ctx: RepairContext) -> MethodResult:
        """Execute repair on ctx.verts, ctx.tris and return MethodResult."""
        repaired_v, repaired_t = my_algorithm(ctx.verts, ctx.tris)
        return MethodResult(
            ok=True,
            verts=repaired_v,
            tris=repaired_t,
            report={"custom_metric": 42},
        )
```

### 2. Auto-Discovery via `builtin/` or Manual Registration
- **Built-in method:** Place your module as `sutura_engine/methods/builtin/<slug>.py`. Export an instance named `METHOD` (or `METHODS` for two variants; or a subclass of `RepairMethod`). When `sutura_engine.methods` initializes, `discover_builtin_methods()` scans the `builtin/` package and registers any discovered methods automatically. Name the module after its user-facing slug and set a `display_name`.
- **Dynamic / Plugin registration:** Register at runtime using:
  ```python
  from sutura_engine.methods import register_method
  register_method(MyCustomMethod())
  ```
- **Custom Templates:** Custom geometric templates can also be registered pluggably via:
  ```python
  from sutura_engine.diagnosis import register_template
  register_template("my_template", my_detection_function)
  ```
The new method immediately participates in `--list-methods`, `--analyze` recommendations, GUI method column selection, and budget-governed triage ranking.

## Rust core performance work (`rust/sutura-geom`)

- **Output-identity rule:** a performance change to the exact arrangement keeps the output identical, not merely equal in face count. Verification is the order-independent digest of `examples/arrangement_digest.rs` (exact rational vertex coordinates + winding; independent of triangle order, vertex numbering and cyclic rotation), compared before/after on thingi10k_1038441, its subsets (produced by `examples/bench_arrangement.rs`) and at least thingi10k_1038439, 55772, 502009, 46012 and artec_metal-nut. `cargo test --release --features cdt-check` additionally asserts every accelerated triangulation query against the linear reference scan; CI runs the Rust tests with and without that feature.
- **Output-changing work is a separate decision:** changes that alter the output (for example Sloan-style queue flipping instead of the Steiner split used for non-convex quadrilaterals) are not performance work. They require an explicit decision and a measurement on the real-world corpus, and are never bundled with an identity-preserving optimisation.
- **Reference input and digest:** the OBJ is converted from `tests/real-world-samples/thingi10k_1038441.stl` with trimesh (5.x; its vertex welding is why the subsets differ slightly from the C1 table in the crate README). The reference digest for the full mesh, identical across C1–C4, is `7b05a6fc3b785f42` (37,323 output faces, 4,445 proper SI pairs). Corpus/test OBJs go to `/tmp`, never into the repo.
- **Measurement (Linux):** `cd rust/sutura-geom && cargo run --release --example arrangement_digest -- /tmp/<mesh>.obj [...]` prints time, face counts and digest per file; `cargo run --release --example bench_arrangement --features profile -- /tmp/<mesh>.obj` gives the per-phase split.
- **Measurement (macOS, conda env `sutura-env`):** build with `PYO3_PYTHON=/opt/homebrew/Caskroom/miniforge/base/envs/sutura-env/bin/python cargo build --release --example arrangement_digest`, then run `DYLD_LIBRARY_PATH=/opt/homebrew/Caskroom/miniforge/base/envs/sutura-env/lib ./target/release/examples/arrangement_digest /tmp/thingi10k_1038441.obj`. `DYLD_LIBRARY_PATH` must not be exported while cargo itself runs (libiconv conflict), and without `PYO3_PYTHON` the example links against a different libpython than the one on `DYLD_LIBRARY_PATH`.
- **Evaluated CDT variants (developer switches, NOT the default):** `cdt2d::experimental` holds per-thread bits (thread-local, so parallel unit tests cannot interfere): 1 = keep constraint flags on `flip` (the default `flip` rebuilds with `Tri::new` and clears the outer-edge flags on the flipped side), 2 = Sloan queue flips instead of split vertices on the constraint, 4 = propagate segment endpoints lying inside a host edge to every triangle sharing that edge (`arrangement::collect_edge_points`; zero-area triangles are kept unchanged). Set them with `SUTURA_CDT_OPTS` (`arrangement_digest`), `sutura_geom._set_cdt_experimental(bits)` or `benchmark_repair_corpus.py --cdt-experimental BITS`. Findings: the reference output has T-junctions exactly where an endpoint lies inside a host edge (bit 4 removes them: 100045 56 -> 0 odd-use edges; regression `propagated_edge_points_remove_t_junctions`), Sloan cuts 1038441 from 37,323 to 32,481 faces and 17.8 s to 13.8 s (regression `sloan_flips_add_no_vertex`), bit 1 has no effect once Sloan is on. End to end on the 40 real-world samples (`--experimental-indirect-autorefine --no-fallback-ftetwild`) strict watertight stays 31/40 for all variants and for the pipeline without the tier; propagation costs ~35 % arrangement time. Default output therefore unchanged; results table in the crate README. Enabling one by default is an output-changing decision (see the rule above).
- **Timing status, thingi10k_1038441 full mesh:** C1 (v0.4.0) 462.7 s on the Apple M2 / 830 s on the x86_64 VM (2 vCPU); C2 29.8 s / 52.5 s; C3 16.8 s / 28.1 s; C4 10.6 s / 17.6 s. Timings are compared only within one machine. Remaining cost on the VM after C4 (profile build): per-host triangulation 7.4 s, classification 4.6 s, implicit point construction 2.3 s, weld and output 0.06 s (the phases overlap in the profile). On the 90k-face meshes (46012, artec_metal-nut) C4 gains only 1–3 %; their cost lies outside these phases and has not been profiled yet.

## Backlog (v0.3 notes — diagnosed, NOT fixed yet)

- **Pre-v0.3 security audit (2026-09, FAZ12):** `docs/security-audit-2026-09.md`
  records the on-release scan. Result: dependencies (pip-audit), shell/
  subprocess patterns, 3MF XML (XXE — regex parser, no XML lib, so safe by
  construction), ZIP (no extract → no zip-slip), path traversal, and hardcoded
  secrets are all CLEAN. Three LOW recommendations deferred to the maintainer:
  checksum/signature verification for install-script downloads (install.sh
  tarball, build_appimage.sh python-build-standalone/appimagetool), GitHub
  Actions commit-SHA pinning (currently major-version pins), and a 3MF
  zip-bomb decompressed-entry size cap (theoretical memory-DoS, judgment call).

- **Extreme mode can WORSEN heavy-self-intersection scans.** 75-model corpus:
  for scan-derived meshes with thousands of self-intersections (e.g.
  thingi10k_804302 has 14,730 SI; Ephebe 2,491 SI + 327 non-manifold),
  aggressive/extreme escalation never reached watertight, and extreme often
  made things worse (thingi10k_147525: 0 -> 159 holes; Athena: aggressive 56
  holes -> extreme 125 + lost two-manifold) because removing self-
  intersecting faces opens more boundary edges. `mode_suggestion_keys` fires
  `sug_holes_many`/`sug_si_*` on exactly these meshes — the suggestion text
  may over-promise extreme's value on heavy-SI scans. Revisit the suggestion
  wording/conditions for v0.3; do not attempt to fix now.

- **fTetWild output fidelity and determinism.** fTetWild is not
  deterministic (output and run time vary between runs even with
  `num_threads=1`), and its result is re-triangulated. Adopted results can
  change the shape where openings and cavities are closed: one-sided
  output-to-input Hausdorff (benchmark, macOS 2026-09-26) 3.7 % of the
  diagonal on thingi10k_1038441, 1.8 % on 1038439, 1.1 % on 224108, 8 % and
  5 % on two corpus meshes. The earlier "28 % on thingi10k_46012" was a
  measurement artifact: pymeshlab's `get_hausdorff_distance(samplevert=True)`
  also samples unreferenced vertices, and the fTetWild bridge output keeps
  every tetrahedron vertex (interior ones included); when no post-process
  compacts the boundary, those interior points dominate the maximum.
  `repair._hausdorff_rel` (used by the benchmark) drops unreferenced vertices
  first.
- **fTetWild time budget.** fTetWild runs under a 180 s budget. On
  artec_metal-nut (89,999 faces) it times out on macOS even unloaded
  (`ftetwild_error='timeout'`, 2 holes left, `warning`; the only strict
  failure of the 40 real-world samples), and on a loaded machine it can time
  out on thingi10k_248395 as well (15 holes left). The budget/timeout
  behaviour (budget size, fTetWild parameters such as the target edge
  length, input reduction, reporting) needs its own treatment.
- **The exact arrangement is SI-free only as exact rationals (float64
  hand-off evaluated, not adopted).** `indirect_bridge.py` rounds the exact
  output to `float32`, and the `si_after: 0` in its report holds only for
  the exact rationals. Measured (2026-09-25, 8 SI meshes, pymeshlab
  self-intersecting faces before/after the stage-1 chain and after the
  final float32 write): self-intersections come back with ANY floating
  representation, not because of float32 in particular. Re-scanning the
  rounded output with the crate's own exact classifier, 1038441 still has
  4,220 proper SI pairs in float64 and 4,068 in float32 (input 4,436);
  small meshes go to 0 (100045, 55772 in float32). float64 is mostly WORSE
  after the chain (1038441 16,402 vs 7,252 SI faces, 1038439 625 vs 221,
  46012 2,040 vs 1,224; metal-nut about equal), because float32 rounding
  merges near-coincident vertices (1,322 on 1038441, 153 on 1038439) so
  those faces share vertices and no longer count as intersecting. The
  arrangement also leaves touch points and coplanar overlaps unresolved by
  design (re-scan of 1038441: ~365k touch points, ~13k coplanar overlaps).
  A float64 hand-off is therefore NOT a fix; the real fix is snap rounding
  inside the Rust core (round the exact output to a float grid without
  creating new intersections, as CGAL's autorefine does), together with
  resolving touch points and coplanar overlaps — a large, output-changing
  project. The CDT variant bits 6 (edge-point propagation + Sloan) lower the
  post-chain SI clearly on dense scans (1038441 7,252 -> 4,036, 46012 1,224
  -> 786, 100281 3,832 -> 3,760) but raise it slightly on 100045 (0 -> 3)
  and 1038439 (221 -> 258); not a default recommendation. Measurement
  scripts were throwaway (/tmp).

  unchanged. Note that STL carries no topology: the split vertices share
  coordinates and weld again when the file is reloaded; the pinch is a
  property of the shape and slicers handle it — the fix corrects the stage-2
  flow and the report. Regression: `tests/test_pinched_vertices.py`.

- **Strict-watertight but `warning` after fTetWild — FIXED.** Diagnosed on
  macOS (224108: 3/3 watertight; 248395: 7/10 watertight, 2 warning, 1
  fTetWild timeout): the warning runs had `holes_remaining=0`,
  `non_manifold_edges_remaining=0`, `two_manifold=false`,
  `manifold_postprocessed=false` and no stage 2, i.e. a pinched vertex on the
  fTetWild boundary; every run with `manifold_postprocessed=true` ended
  watertight. The manifold3d post-process now also triggers on a closed but
  not two-manifold boundary (see the fTetWild bullet in How it runs).

- **LOD overshoot on ~17/74 corpus models — FIXED.** `_decimate_lod` used a
  "closest to target" selection that could pick an ABOVE-target step when
  the next step overshot below by a similar margin (measured up to 5.5k tris
  vs target 3500). It now picks the result AT OR BELOW the target that is
  closest to it (never above, never over-collapsing when a step jumps far
  below), with a finer ascending step list `(1.0, 1.5, 2.0, 3.0, 5.0, 8.0)`.
  Verified on all 17 overshoot models (now 1,616-3,368 tris, all <= target)
  and 5 of them re-timed (FPS 44-46 -> 64-98, all >= 64 FPS). Small meshes
  at or below the target are returned unchanged.

## Release checklist

Get the user's explicit go-ahead to start a release, asked for by name
("should I cut vX.Y.Z now?"), before step 1 — green CI, a merged PR, or
a backlog note that a release is pending are not that go-ahead (see
Merge and release approval above). Once given, run ALL of the
following in order, without being asked separately for each step:

1. Bump the version constant (repair.py) — batch bumps, don't bump on every
   commit (see Conventions).
2. Update CHANGELOG.md with a real entry for this version.
3. Commit the version bump with a summary body.
4. Tag the release (vX.Y.Z).
5. **Version-history standing rule (FAZ15):** if this version ADDS a
   user-facing feature/capability, add a short entry to the "Version history"
   ("Sürüm geçmişi") section in README.md AND README.tr.md (one line, what
   came in, based on the CHANGELOG Added/Changed user-visible items). Fix-only
   versions do NOT touch that section.
6. Feature Status table audit (README.md/tr.md) against the actual commits
   since the previous tag — bump percentages only when the honest state
   changed; check the test-suite list in the 'Test coverage' row is current.
7. Re-run scripts/generate_screenshots.py if the GUI's visible state changed
   since assets/ was last generated (check via git log --follow).
8. Publish the release from the maintainer's machine with the maintainer's own
   `gh` (a user token):
   `gh release create vX.Y.Z --target main --title vX.Y.Z --notes-file <notes>`.
   This creates the tag `vX.Y.Z` at `main` AND publishes the release as the
   user, which is what fires the `release: published` workflows (the three
   build workflows attach the AppImage/.dmg/prebuilt wheels and
   `publish-orcacloud.yml` publishes the plugin). Never create or publish the
   release from a workflow with the automatic `GITHUB_TOKEN` — GitHub does not
   start workflow runs for `GITHUB_TOKEN`-authored events, so
   `release: published` would never fire and the OrcaCloud publish would
   silently never run.
9. Verify the release notes actually landed as written: after
   `gh release create` / `gh release edit`, run
   `gh release view <tag> --json body` and read the ACTUAL body back.
   Confirm it contains the real highlights list for this version — not a
   generic template blurb, not empty, not truncated. A `gh release
   create`/`edit` call returning success is not proof the content is
   correct; heredocs and multi-line --notes strings can silently get
   mangled by shell quoting. If the body is wrong, edit it again and
   re-verify — do not consider the release done until the displayed body
   matches what was intended.
10. **Verify prebuilt wheels workflow (`build-sutura-geom.yml`):** ensure that
   `build-sutura-geom.yml` is green and its prebuilt wheels (`sutura_geom` abi3
   wheels for Linux and macOS) plus `sutura_geom-SHA256SUMS` are attached to the
   release before announcing it (installers, updater, and bundles depend on these
   assets).

11. **OrcaCloud plugin auto-publish (standing, automatic since 2026-09):**
   every published GitHub Release triggers
   `.github/workflows/publish-orcacloud.yml` via OIDC trusted publishing.
   The plugin's OrcaCloud version is NOT tracked independently anymore -- it
   follows this release's own tag (`github.event.release.tag_name`), and the
   changelog field is this release's own body text. The workflow diffs
   `orcaslicer-plugin/` between this tag and the previous one and SKIPS the
   OrcaCloud publish step entirely if the plugin file did not change -- so a
   release with no plugin changes does not spam a new, unrelated Cloud
   version. No manual Cloud upload/paste step is needed anymore; do not
   revert to doing it by hand out of habit. If the plugin file DID change,
   verify after the fact that the new version actually appears on the Orca
   Cloud listing page (Actions tab -> workflow run -> check the "Publish
   release to OrcaCloud" step didn't get skipped and returned 2xx).
   Since v0.4.1 the step prints the API response and fails on anything but
   HTTP 201 (it used to report success on a 400). The metadata JSON is sent
   with `curl --form-string` because `-F` splits the value at `;`. The
   OrcaCloud side only accepts OIDC tokens from the `release` event, so a
   failed publish is retried by turning the release into a draft and
   publishing it again (same tag, re-fires `published`), never by
   `workflow_dispatch` (which is rejected with HTTP 401). The OrcaCloud
   **listing description** is a free-text field in the OrcaCloud
   Create/Edit-plugin web dialog, not a repository file and not part of the
   publish API payload, so it is maintained manually in the OrcaCloud UI.

This checklist is the release process — steps 5 and 6 are not optional
extras to be reminded about separately; they are part of doing a release at
all.

General principle for this whole checklist: a command exiting 0 means
the command ran, not that its output is correct. For every step that
produces user-facing content (CHANGELOG entry, commit body, README
section, GitHub Release notes), read back what was actually written
before moving to the next step. This applies beyond releases too —
whenever a tool call's success is being used as evidence that content is
correct, verify the actual content instead of trusting the exit status.
